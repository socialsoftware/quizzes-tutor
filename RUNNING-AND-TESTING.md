# Running and testing locally

Practical notes for running Quizzes Tutor on a developer machine: where the demo data comes
from, how to run against a database dump, and how to run each test suite.

Prerequisites: Java 25, Node 24, PostgreSQL, and `psql` on the `PATH` (`package.json` accepts
Node 22.12 and above; 24 is what CI and the Docker images use). Maven does not
need to be installed — `backend/mvnw` downloads the version the project pins.

---

## 1. Where the demo quizzes come from

Demo content is **generated by the backend**, not stored in a fixture file.

`DemoUtils.resetDemoInfo()` runs on every backend startup
(`TutorApplication.afterPropertiesSet()`) and again every day at 01:00
(`config/ScheduledTasks.java`, cron `0 0 1 * * *`). Under the `dev` and `prod` profiles it calls
`DemoService.populateDemo()`, which creates:

- two topics — *Software Architecture* and *Software Engineering*
- one assessment — *Software Engineering Questions*
- four quizzes — *In Class Quiz One Way*, *In Class Quiz*, *Teacher Proposed*, *Non Scrambled*

**Caveat.** Questions are only attached to those quizzes when their id appears in a hard-coded
list in `demo/DemoService.java`:

```java
List<Integer> questions2Keep   = Arrays.asList(1320, 1940, 1544, 11081, 11082);
List<Integer> questionsInQuizzes = Arrays.asList(1940, 11081, 11082);
Integer quiz2Keep = 40438;
```

These are ids from the production database. On a fresh/empty database they don't exist, so the
four quizzes are still created but end up **with no questions**, and a quiz with no questions
never shows up for a student. Restoring a production dump makes the demo work as intended.

### Getting usable demo quizzes

1. **Run against a production dump** (see section 2) — the demo quizzes are regenerated with
   their questions on every startup. Easiest option.
2. **Create them by hand:** log in with *Demo as teacher*, then
   `Management → Questions → New Question` (fill title, content, the four options, and toggle the
   switch on the correct one). With at least two questions,
   `Management → Quizzes → New Quiz → Submit Query`, set a title and an **Available Date** that is
   not in the future, add the questions with their `add` action, and Save.
3. **Seed with Cypress:** `tests/e2e/specs/teacher/manageQuizzes.js` already builds two questions
   and a quiz in its `beforeEach` (`cy.createQuestion`, `cy.createQuizzWith2Questions`). To use it
   as a seeder, copy the spec and drop the `beforeEach`/`afterEach` hooks — otherwise the
   `afterEach` deletes everything it just created.

## 2. Running the backend against a database dump

```bash
# optional: create the dump's owner role to avoid thousands of harmless ownership errors
sudo -u postgres psql -c "CREATE ROLE ars;"

# restore into a separate database, leaving the dev one untouched
psql -h localhost -U <user> -d postgres -c "CREATE DATABASE tutordb_import;"
psql -h localhost -U <user> -d tutordb_import -v ON_ERROR_STOP=0 -f /path/to/dump.sql

psql -h localhost -U <user> -d tutordb_import -c "SELECT count(*) FROM quizzes;"
```

`ERROR: role "ars" does not exist` messages only affect `ALTER ... OWNER TO` statements; the
schema and data are restored regardless (the tables end up owned by the restoring user).

Point the backend at it in `backend/src/main/resources/application-dev.properties`:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/tutordb_import
```

> `application.properties` sets `spring.jpa.hibernate.ddl-auto=update`, so Hibernate may add
> columns/tables to the restored schema at startup. It is additive, but keep the original dump.

Start it:

```bash
cd backend
./mvnw -Pdev spring-boot:run     # add -o to work offline
# wait for "Started TutorApplication in ... seconds"
```

> After switching databases, log out in the browser (or clear `localStorage`). The frontend keeps
> `token` and `currentCourse` there, and a course execution id from the previous database makes
> the API answer `403`.

## 3. Test suites

### Backend unit tests — Spock, H2 in memory, no database needed

```bash
cd backend
./mvnw clean -Ptest test
```

91 `*Test.groovy` files, 601 tests. Reports in `target/surefire-reports/`, coverage in
`target/site/jacoco/`.

### Backend integration tests — 36 `*IT.groovy`, needs PostgreSQL

```bash
cd backend
PSQL_INT_TEST_DB_USERNAME=<user> PSQL_INT_TEST_DB_PASSWORD=<password> \
  ./mvnw clean verify -Ptest-int
```

> **These tests write to and delete from the database.** `application-test-int.properties` points
> at `localhost:5432/tutordb`, the same database the `dev` profile uses. Never run them while the
> datasource points at a database whose contents you care about. Prefer a throwaway one:
>
> ```bash
> psql -h localhost -U <user> -d postgres -c "CREATE DATABASE tutordb_test;"
> PSQL_INT_TEST_DB_USERNAME=<user> PSQL_INT_TEST_DB_PASSWORD=<password> \
>   ./mvnw clean verify -Ptest-int \
>   -Dspring.datasource.url=jdbc:postgresql://localhost:5432/tutordb_test
> ```

### Frontend unit tests — vitest, no servers needed

```bash
cd frontend
npm run test:unit
```

### Frontend end-to-end tests — Cypress

Needs the backend on `:8080`, the frontend on `:8081`, `psql` on the `PATH`, and
`frontend/cypress.env.json` (copy it from `cypress.env.json.example`) holding
`psql_db_name`, `psql_db_username`, `psql_db_password`, `psql_db_host`, `psql_db_port`.

```bash
cd frontend
npm run test:e2e                                                   # headless, all specs (Firefox)
npx cypress run                                                    # bundled Electron (deprecated)
npx cypress run --spec "tests/e2e/specs/teacher/manageQuizzes.js"  # single spec
npm run cypress                                                    # interactive runner
```

> **Use Firefox, not the bundled Electron.** Cypress 16 deprecates Electron, and its renderer
> dies partway through the longer specs: the page goes blank and the next selector times out.
> The same suite scores **34/55 on Electron and 54/55 on Firefox**, so `test:e2e` and CI both
> pass `--browser firefox`. Run it on an otherwise idle machine either way — running the suite
> alongside a Maven build took it from 2 failing specs to 8.
>
> The one remaining failure, `student/createRandomQuiz.js`, predates this and is unrelated.

> **The suite is destructive.** `cy.deleteQuestionsAndAnswers()` in
> `tests/e2e/support/database.js` issues `DELETE FROM` with no `WHERE` clause against
> `code_order_answer_slot`, `code_order_slot`, `replies`, `discussions`, `answer_details`,
> `question_answers`, `quiz_answers`, `quiz_questions`, `quizzes`, `topics_topic_conjunctions`,
> `topic_conjunctions`, `topics_questions`, `assessments`, `reviews`, `question_submissions`,
> `options`, `question_details`, `questions` and `topics`. Other helpers
> (`afterEachTournament`, `cleanTestCourses`, `deleteWeeklyScores`, …) delete as well.
> Point `cypress.env.json` at a disposable database only — running the suite against a restored
> production dump will wipe its content, demo quizzes included.

### Backend load tests — JMeter

The `.jmx` plans in `backend/jmeter/` are not wired into Maven; run them with a standalone
[Apache JMeter](https://jmeter.apache.org) 5.x, with the backend already running. Run from the
plan's own directory, since the CSV data sets are referenced by bare filename.

```bash
cd backend/jmeter/answer
jmeter -n -t quiz-answer-muliple-choice.jmx \
  -Jserver=localhost -Jport=8080 -Jprotocol=http -Jprefix= \
  -Jnumber_of_students=200 -Jnumber_of_questions=20 \
  -l results.jtl -e -o report/          # open report/index.html
```

Available plans:

| Folder | Plans |
|---|---|
| `answer/` | `quiz-answer-muliple-choice.jmx` (200 students × 20 questions), `quiz-answer-code-fill-in.jmx`, `fraud-report-load.jmx`, `fraud-communication-load-as.jmx`, `fraud-communication-load-es.jmx` |
| `dashboard/` | `dashboard.jmx` (10 students × 10 questions) |
| `administration/` | `WSCreateExternalCourseExecutionTest.jmx`, `WSCreateExternalCourseExecutionLoadTest.jmx`, `WSGetExternalCourseExecutionsLoadTest.jmx` (100 threads × 10 loops) |
| `question/` | `WSCreateStudentQuestionLoadTest.jmx` |

Two things to watch out for:

1. `fraud-communication-load-as.jmx` and `fraud-communication-load-es.jmx` default to the
   **production** host (`quizzes-tutor.tecnico.ulisboa.pt:443`). Always pass
   `-Jserver=localhost -Jport=8080 -Jprotocol=http`.
2. The plans under `administration/` and `question/` open a JDBC connection with the user `ars`
   by default. Override it (`-JPSQL_USERNAME=... -JPSQL_PASSWORD=... -JPSQL_PORT=...`) and copy a
   `postgresql-*.jar` driver into `$JMETER_HOME/lib/`, which JMeter does not ship.

## 4. Bringing the whole stack up

Three terminals:

```bash
# 1 — database
pg_isready                         # expect: accepting connections
# sudo systemctl start postgresql  # if it isn't

# 2 — backend (pick the database in application-dev.properties first)
cd backend
./mvnw -Pdev spring-boot:run

# 3 — frontend
cd frontend
cp example.env .env                # first time only; VUE_APP_ROOT_API=http://localhost:8080
npm ci                             # first time only
npm run dev                        # http://localhost:8081
```

Health checks:

```bash
curl -s -o /dev/null -w "backend %{http_code}\n"  http://localhost:8080/api-docs
curl -s -o /dev/null -w "frontend %{http_code}\n" http://localhost:8081/
curl -s "http://localhost:8080/auth/demo/student?createNew=false" | head -c 200
```

Then open `http://localhost:8081` and use the *Demo as student* / *Demo as teacher* buttons.

### Docker Compose

`docker-compose.yml` also defines `postgres`, `backend`, `frontend`, `fraud-service` and the
`be-unit-tests` / `integration-tests` / `fe-unit-tests` one-shot services:

```bash
docker compose up
docker compose run --rm be-unit-tests
docker compose run --rm integration-tests
docker compose run --rm fe-unit-tests
```

Before that works you must copy the environment templates, which are only committed as examples:

```bash
cp data/env/backend.dev.env.example       data/env/backend.dev.env
cp data/env/database.dev.env.example      data/env/database.dev.env
cp data/env/fraud-service.dev.env.example data/env/fraud-service.dev.env
```

Note that Compose publishes PostgreSQL on host port **5433**, while `application-dev.properties`
and `application-test-int.properties` expect **5432**. Running the backend build on the host against the
Compose database needs `-Dspring.datasource.url=jdbc:postgresql://localhost:5433/tutordb`.
